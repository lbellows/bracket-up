# Publishing BracketUp on F-Droid

BracketUp is a good fit for F-Droid: MIT licensed, fully offline, no analytics or
advertising, no Google Play Services, and it ships with **zero Android permissions**.

There are two destinations, and it is worth using both:

| | IzzyOnDroid | F-Droid main repo |
|---|---|---|
| Who builds the APK | you (GitHub Actions) | F-Droid, from source |
| Who signs it | you | F-Droid |
| Time to listing | days | weeks to months |
| Shows in F-Droid client | after the user adds the Izzy repo | by default |

Ship to IzzyOnDroid first so people can install the app now, then submit to the
main repo. Both read their store listing from `fastlane/metadata/android/en-US/`
in this repo, so the description, screenshots and changelogs are already in place.

---

## What is already set up

- `android/` is committed, generated by `npx expo prebuild`. F-Droid's buildserver
  compiles this directory, so it must stay in sync with `app.json` — CI enforces that.
- All five default permissions (`INTERNET`, `SYSTEM_ALERT_WINDOW`,
  `READ_EXTERNAL_STORAGE`, `WRITE_EXTERNAL_STORAGE`, `VIBRATE`) are stripped via
  `android.blockedPermissions` in `app.json`. None of them were used.
- `plugins/withReleaseSigning.js` adds a release signing config that activates only
  when a keystore is actually configured. With no keystore it leaves the APK
  unsigned — which is exactly what F-Droid wants, since it signs with its own key —
  rather than falling back to the debug key. That means **no keystore of any kind is
  committed to this repository**, not even the public Android debug key.
- `.github/workflows/release.yml` builds a signed universal APK on any `v*` tag,
  verifies it declares no permissions, and attaches it to a GitHub Release.
- `fdroid/com.bracketup.app.yml` is the recipe to submit to fdroiddata.
- Version numbers live in `app.json` (`expo.version` and `expo.android.versionCode`).
  EAS was removed entirely (`eas.json` and the `extra.eas` project binding), so the
  repo is the single source of truth — F-Droid reads the version from source and
  cannot see EAS's server anyway.
- `plugins/withoutUpdatesMetadata.js` strips the `expo.modules.updates.*` manifest
  entries the Expo template emits by default. `expo-updates` is not a dependency;
  over-the-air JS updates are the main thing F-Droid objects to in Expo apps, so the
  manifest should not advertise a mechanism the app does not have.

## One-time setup

### 1. Release keystore — done

The signing key already exists:

| | |
|---|---|
| Keystore | `~/.android-signing/bracketup-release.keystore` |
| Password | `~/.android-signing/bracketup-release.password` (mode 600) |
| Alias | `bracketup` |
| Key | RSA-4096, PKCS12, valid until 2054-01-14 |
| SHA-256 | `F3:97:8A:B0:A5:03:BA:CB:8B:58:4D:AF:9E:E9:7B:4E:05:25:75:85:23:D1:A2:32:04:42:37:A3:5E:97:B5:64` |

It was generated with `openssl` rather than `keytool`, because no JDK is installed
on this machine. The result is a PKCS12 keystore — the same format `keytool` has
produced by default since JDK 9 — and Gradle reads it with no extra configuration.
The store password and key password are identical, as PKCS12 requires.

> **Back this up now, somewhere off this machine.** The key identifies BracketUp
> forever. Lose it and IzzyOnDroid users cannot upgrade: they must uninstall and
> reinstall, losing their saved tournaments. Both files matter — the keystore is
> useless without its password.

To recreate an equivalent key elsewhere (with a JDK available):

```bash
keytool -genkeypair -v \
  -keystore bracketup-release.keystore \
  -alias bracketup \
  -keyalg RSA -keysize 4096 -validity 10000
```

Keep any keystore **outside this repository**. `*.keystore` is gitignored as a
backstop, but do not rely on that.

### 2. GitHub signing secrets — done

All four are set on `lbellows/bracket-up` (verify with `gh secret list`):

| Secret | Value |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | `base64 -w0` of the keystore |
| `ANDROID_STORE_PASSWORD` | the keystore password |
| `ANDROID_KEY_PASSWORD` | same as the store password |

The key alias (`bracketup`) is set as a literal in the workflow rather than a
secret. It is not sensitive — `apksigner` prints it from any signed APK — and
storing it as a secret made GitHub redact the string "bracketup" from every log
line, including the app's own package name.

GitHub secrets are write-only, so these cannot be read back — if the local copies
are ever lost, the key is lost with them. To rotate, re-run:

```bash
KS=~/.android-signing/bracketup-release.keystore
PASS=$(cat ~/.android-signing/bracketup-release.password)
base64 -w0 "$KS" | gh secret set ANDROID_KEYSTORE_BASE64 --repo lbellows/bracket-up
printf '%s' "$PASS" | gh secret set ANDROID_STORE_PASSWORD --repo lbellows/bracket-up
printf '%s' "$PASS" | gh secret set ANDROID_KEY_PASSWORD --repo lbellows/bracket-up
```

### 3. Building locally (optional)

Create `android/keystore.properties` (gitignored):

```properties
storeFile=/absolute/path/to/bracketup-release.keystore
storePassword=...
keyAlias=bracketup
keyPassword=...
```

Then `cd android && ./gradlew assembleRelease`. This needs JDK 17, the Android SDK,
**and the NDK plus CMake** — `react-native-reanimated`, `react-native-worklets` and
`react-native-screens` compile C++ from source because the new architecture is
enabled. That is roughly 10-15 GB of toolchain, and none of it is installed on this
machine, so CI is the easier path:

```bash
sudo pacman -S jdk17-openjdk
# unzip Google's commandlinetools-linux-*.zip into ~/Android/Sdk/cmdline-tools/latest
sdkmanager "platform-tools" "build-tools;35.0.0" "platforms;android-35" \
           "ndk;27.1.12297006" "cmake;3.22.1"
```

## Cutting a release

1. Bump both numbers in `app.json`. `versionCode` must increase by at least one
   every release; `version` is what users see.

   ```jsonc
   "version": "1.0.1",
   "android": { "versionCode": 2 }
   ```

2. Regenerate the native project and confirm nothing else drifted:

   ```bash
   npm run prebuild
   npm run prebuild:check
   ```

3. Write the changelog at `fastlane/metadata/android/en-US/changelogs/<versionCode>.txt`
   — so `changelogs/2.txt` for versionCode 2. The filename is the versionCode, not
   the version name. `prebuild:check` fails if it is missing, because a mismatch
   otherwise just shows up as an empty changelog on both stores.

4. Commit, tag, push:

   ```bash
   git commit -am "release: 1.0.1"
   git tag v1.0.1
   git push origin main --tags
   ```

The release workflow builds, verifies and publishes the APK to GitHub Releases.

## Submitting to IzzyOnDroid

Once your first tagged release with an attached APK exists:

1. Open an issue at <https://gitlab.com/IzzyOnDroid/repo/-/issues> using the
   "Inclusion request" template.
2. Give it the repo URL `https://github.com/lbellows/bracket-up` and the package
   name `com.bracketup.app`.
3. Izzy's scanner checks the APK for tracking libraries and non-free blobs. There
   are none, so this should pass without changes.

After inclusion, every new GitHub Release is picked up automatically — you do not
file anything again. Users install by adding
`https://apt.izzysoft.de/fdroid/repo` as a repository in the F-Droid client.

## Submitting to the F-Droid main repo

1. Fork <https://gitlab.com/fdroid/fdroiddata>.
2. Copy `fdroid/com.bracketup.app.yml` from this repo to
   `metadata/com.bracketup.app.yml` in your fork, and set `commit:` to the tag you
   released (e.g. `v1.0.1`) with the matching `versionName` / `versionCode`.
3. Test the recipe if you can — it needs Docker and a lot of disk:

   ```bash
   fdroid build -v -l com.bracketup.app
   ```

4. Open a merge request. Review is slow and reviewers do ask questions; the common
   ones for this app are answered in the recipe's `MaintainerNotes`.

Things a reviewer may raise, and where they stand here:

- **Prebuilt binaries in `node_modules`.** Covered by `scanignore`. React Native's
  Gradle plugin and the Hermes compiler are build-time tools; the native libraries
  in the APK are compiled during the build from Maven-hosted sources.
- **The JitPack repository in `android/build.gradle`.** Nothing currently resolves
  from it — it is part of the Expo template. If a reviewer objects, it can be
  removed with a config plugin.
- **Why `android/` is committed.** So the buildserver does not have to run
  `expo prebuild` (which fetches templates at build time). CI proves the committed
  project matches `app.json`.

## Development caveat

`INTERNET` is stripped from the manifest, so a locally built dev APK
(`npm run android`) cannot reach the Metro bundler. Develop with `npx expo start`
and Expo Go, or `npm run web`. If you need a dev build that talks to Metro,
temporarily remove `android.permission.INTERNET` from `blockedPermissions` in
`app.json`, run `npm run prebuild`, and revert both before releasing —
`prebuild:check` will catch it if you forget.
